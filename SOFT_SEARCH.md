# Мягкий отбор в исходном GeoGen

Режим `policy: soft` использует исходный генератор GeoGen: полный перечень
допустимых продолжений, его DFS, канонизацию и раннее отсечение невозможной
симметрии. Параметры proposals/keep/targetRatio в этом режиме не используются.

Обновление и сборка из ветки с текущими доработками:

```bash
git fetch origin
git switch feature/family-discovery
git pull --ff-only origin feature/family-discovery
bash build.sh build --output ./dist/geometry-suite-soft --test
```

Старый кэш можно передать через --state /путь/к/старому/.builder.
Исходные репозитории обновлять вручную не нужно: текущий сборщик применяет
19 патчей, включая необязательный [ранговый отбор](RANK_SEARCH.md).
Для нового output укажите ещё не существующий каталог.

## Как выключить влияние новой оценки

```json
{
  "version": 1,
  "policy": "soft",
  "seconds": 600,
  "keepOutsideTargetsPercent": 100,
  "phases": [{}]
}
```

При отсутствии частичных rankIntervals/finalRankInterval значение 100
означает сохранять все продолжения. При выключенном collectReference
даже расчёт метрики не добавляется. Конструктор и поиск теорем вызываются
в прежнем количестве и порядке. Исправления прувера и проверяющих, внесённые
ранее, при этом сохраняются: речь об исходном алгоритме генерации текущего
форка, а не об откате всего репозитория к старому коммиту.

## Как постепенно смещать поиск

Пример границ в понятных единицах; это иллюстрация, не оптимальные значения:

```json
{
  "version": 1,
  "policy": "soft",
  "seconds": 600,
  "seed": 61,
  "keepOutsideTargetsPercent": 90,
  "phases": [{"theoremsPerPoint": {"min": 2}}],
  "final": {"newPointTheorems": {"min": 1, "max": 3}}
}
```

- На промежуточных этапах желательно не менее двух найденных теорем на точку.
- На последнем разрешённом шаге — от одной до трёх теорем с новой точкой.
- Внутри границ сохраняются все продолжения.
- Вне границ сохраняются случайные 90%, остальные 10% отсекаются вместе
  со своими потомками прямо внутри генерации конфигураций.

Чем ниже keepOutsideTargetsPercent, тем сильнее влияние границ. Это процент
сохранения НЕПОДХОДЯЩЕГО продолжения на отдельном этапе, а не доля общего
времени поиска или гарантия сохранения такого процента конечных задач.
При нескольких отсечениях вероятность прохождения ветви перемножается.
Последняя запись phases повторяется, когда этапов больше, чем записей.
Запись final заменяет её на последнем шаге по лимиту итераций или объектов,
независимо от количества завершённых симметричных блоков.

Теорема считается один раз по идентичности утверждения GeoGen. По умолчанию
все веса равны 1: theoremsPerPoint — T/N, newPointTheorems — число найденных
теорем, где участвует новая точка. Можно задать только min, только max
или обе границы. Пустая запись {} не задаёт предпочтений. При отсутствии
целевых границ отбор не включается даже при проценте меньше 100.

Для среднего по нескольким новым точкам считается, во скольких теоремах
участвует каждая, затем берётся среднее. Утверждение про две новые точки
попадает в счётчик каждой. Если на этапе новых точек нет, граница
newPointTheorems к нему не применяется. Поддерживаются до 63 явно названных
точек при расчёте метрики; нейтральный режим без метрики этого ограничения
не добавляет. Optional TypeWeights/LocalTheoremWeight меняют единицы на веса;
начинать подбор лучше с весов 1.

## OnlySymmetric и OnlyFullySymmetric

До вычисления координат сохранена штатная проверка, можно ли завершить
симметрию при оставшихся итерациях, построениях и лимитах объектов.

Предпочтения применяются только когда конфигурация уже удовлетворяет
запрошенному виду симметрии. Асимметричный промежуточный кусок будущей
симметричной конфигурации по новой метрике не отбрасывается.

Этап в phases — переход между такими завершёнными конфигурациями.
В обычном GenerateBothSymmetricAndAsymmetric каждое добавление — новый этап.
В OnlyFullySymmetric три середины сторон могут составить один этап;
newPointTheorems тогда усредняется по всем трём новым точкам. OnlySymmetric
требует хотя бы одной симметрии, а не обязательно всех перестановок вершин.
Поэтому количество этапов зависит от режима и сюжета и видно в калибровке.

## Откуда брать границы: контрольная калибровка

```bash
./dist/geometry-suite-soft/geometry-suite calibrate-search \
  ./examples/search/stories/altitudes-symmetric.txt \
  ./examples/search/stories/incircle-symmetric.txt \
  --output ./calibration-001 --budget 10m --seeds 17 29 43
```

Программа запускает исходный поиск без смещения, отдельно для каждого
сюжета, первого построения и seed. Сохраняются все определения и условия;
варьируется только порядок независимых определений и обхода операций.
В каждой серии фиксируется первое построение, остальные продолжения
получаются исходным перебором. Статистика собирается на C#; Python только
запускает отдельные процессы и сводит готовые отчёты после завершения серий.
Прувер и Extending в калибровке не запускаются — здесь измеряется генерация.

Что получается:

- CALIBRATION.md — медиана и квартили по каждому сюжету и этапу;
- calibration.json — все счётчики, гистограммы, покрытие первых построений,
  seeds, ошибки и число завершённых серий;
- family-00-neutral/gentle/moderate/strong.json — одинаковые границы с
  сохранением соответственно 100/90/70/30% неподходящих продолжений.

В предложенных границах промежуточные этапы требуют верхнюю четверть контрольного
T/N, последний — нижнюю четверть положительного числа теорем с новыми
точками, минимум одну. Для final собирается отдельное распределение,
объединяющее последние шаги с разным числом предшествующих блоков.
Если данных для final недостаточно, эта настройка не генерируется.
Это конкретный пример расписания «сначала много
связей, затем мало», а не обязательная схема задач.

Каждая непустая серия имеет одинаковый вес: быстрая серия с 10000 картинками
не заглушает медленную со 100. Разные сюжеты не сваливаются в одно распределение.
Границы не выставляются при менее 30 наблюдениях или трёх непустых сериях
на этапе. Смотрите реальное покрытие: ограниченный бюджет оставляет только
часть аргументов каждого первого построения. Это сбалансированная контрольная
выборка с указанным покрытием, не доказанная равномерная выборка всего пространства.

Временной budget ограничивает всю калибровку, включая запуск процессов.
При слишком маленьком бюджете часть серий или этапов останется без статистики.
Увеличьте бюджет и проверьте устойчивость квартилей на других seeds.

## Проверка выбранных границ

```bash
cp ./calibration-001/family-00-gentle.json ./my-soft.json
./dist/geometry-suite-soft/geometry-suite run \
  ./examples/search/stories/altitudes-symmetric.txt \
  --search-config ./my-soft.json --output ./runs/soft-001 \
  --timeout 660 --workers 1 --check-ms 2000 \
  --standard-checks --quality-checks --view
```

Номер family соответствует сюжету в CALIBRATION.md. Для нового output
выбирайте новое имя. Отсутствие графической сессии требует убрать --view.
Нейтральный контроль запускается с теми же границами и процентом 100.

Порядок подбора:

1. Зафиксировать сюжеты, глубину, режим симметрии и лимиты проверок.
2. Получить контрольные распределения и выбрать диапазоны в реальных единицах.
3. Сравнить 100/90/70/30% при одинаковом времени и seeds, отсутствовавших
   в калибровке. Сначала менять только этот процент, затем сами границы.
4. Повторить на других сюжетах, не использованных для выбора границ.
5. Сравнить выход прошедших фильтры задач за время, долю таймаутов/ошибок,
   затем вручную сложность, содержательность и повторы в обезличенных выборках.

Меньшая плотность и попадание в границы не являются оценкой качества задачи.
При положительном смещении результат может быть хуже контроля. Ни автоматический
оптимум, ни соответствие уровню IMO-6 этот прототип не устанавливает.

В search-trace.jsonl записываются число ранних отсечений симметрии,
попыток построения, вызовов finder, расчётов метрики и отбраковок по границам.
При collectReference=true добавляется search-reference.json. Эта диагностика
работает и при проценте 100, но тогда добавляет расчёт метрик для статистики;
порядок генерации не меняется. Без диагностики расчёта метрик на 100% нет.

seconds ограничивает поиск между кандидатами. Один долгий вызов канонизации
или прувера может выйти за него; --timeout остаётся внешним предохранителем.
Настройки старого batch-эксперимента сохранены в policies/legacy-batches.
В мягком режиме его proposals, keep, targetRatio, emitFromDepth и
requireNonLocalTheorem не участвуют. Новых геометрических условий не вводится.

Точный ранг среди детей одного родителя доступен через rankIntervals:
[RANK_SEARCH.md](RANK_SEARCH.md). Контрольные квартили этой команды по-прежнему
относятся к выборке сюжета и этапа, а не к списку детей отдельного родителя.
