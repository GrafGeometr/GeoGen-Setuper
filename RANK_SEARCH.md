# Точный ранговый интервал

Для каждого родителя оценивается полный список его допустимых следующих
построений. Ранг локальный: сравниваются дети именно этого родителя, а не
статистика других картинок. Поиск и расчёт оценок выполняются на C#.

## Обновление установленного сборщика

В терминале перейдите в свой каталог GeoGen-Setuper. Для прежнего расположения:

```bash
cd ~/Documents/geometry/GeoGen/GeoGen-Setuper
git status --short
git fetch origin
git switch feature/family-discovery
git pull --ff-only origin feature/family-discovery
bash build.sh build --output ./dist/geometry-suite-rank --jobs 2 --test
./dist/geometry-suite-rank/geometry-suite doctor
```

Если Git сообщает о конфликтующих локальных изменениях, сохраните их до
переключения; команды выше их не сбрасывают. Повторять deps при уже установленных
системных зависимостях не нужно. Если dist/geometry-suite-rank уже существует,
укажите новое имя и используйте его во всех последующих командах.

Один git pull не обновляет готовый комплект: build обязателен. Сборщик получает
закреплённые исходники GeoGen/Geometry/GeometryExtending и применяет все
16 патчей, включая ранговый отбор. Отдельно обновлять или патчить GeoGen не нужно.
Старый установленный комплект сохраняется. Кэш по умолчанию — .builder рядом
с build.sh; для другого кэша добавьте --state /путь/к/старому/.builder.

## Установка на новый Linux

Автоматическая установка системных пакетов предусмотрена для Debian/Ubuntu:

```bash
git clone --branch feature/family-discovery --single-branch \
  https://github.com/GrafGeometr/GeoGen-Setuper.git
cd GeoGen-Setuper
bash build.sh deps
bash build.sh build --output ./dist/geometry-suite-rank --jobs 2 --test
./dist/geometry-suite-rank/geometry-suite doctor
```

Для clone нужен установленный git. deps ставит системные пакеты через apt/sudo.
build загружает закреплённые исходники, инструменты и библиотечные зависимости,
поэтому скачивания при первой сборке ожидаемы. Для --offline уже должны быть
доступны исходники, инструменты и все кэши. Готовый комплект содержит свой
.NET runtime и Java runtime; Python 3 и системные библиотеки остаются нужны.
--test дополнительно запускает тесты C# и Extending; smoke запускается сборщиком
в любом случае. Графическое окно проверяйте отдельно в своей графической сессии.

## Первый запуск

Все дальнейшие команды выполняются из каталога сборщика:

```bash
suite="./dist/geometry-suite-rank/geometry-suite"
cp ./examples/search/policies/rank-middle.json ./my-rank.json
"$suite" run ./examples/search/stories/incircle-symmetric.txt \
  --search-config ./my-rank.json --output ./runs/rank-001 \
  --timeout 660 --workers 1 --check-ms 2000 \
  --standard-checks --quality-checks --view
```

Для своего сюжета замените путь на ./stories/Shaltay.txt или другой story.
output должен быть новым каталогом. Без DISPLAY/WAYLAND_DISPLAY уберите --view.
При проблемах с графическим ускорением попробуйте добавить --software.

| Аргумент | Назначение |
|---|---|
| --search-config | JSON с режимом и расписанием рангов |
| --output | Отдельная очередь, результаты и журналы запуска |
| --timeout 660 | Внешний лимит процесса GeoGen, в секундах |
| --workers 1 | Число параллельных обработчиков находок; это не число потоков генератора |
| --check-ms 2000 | Лимит одной проверки Extending, в миллисекундах |
| --standard-checks | Включить существующий отбор коротких стандартных следствий |
| --quality-checks | Проверить исходное утверждение на независимых численных примерах и записать отчёт |
| --view | Сразу открыть ленту Geometry |
| --no-check | Не запускать Extending; результаты отмечаются unchecked |

В JSON seconds=600 ограничивает сам поиск; --timeout задавайте с запасом.
После завершения GeoGen очередь находок продолжает обрабатываться, поэтому
общее время команды может быть больше обоих чисел. --no-check подходит для
диагностики генерации, но не для оценки количества прошедших Extending задач.

Сюжет по-прежнему задаёт исходную картинку, допустимые операции и бюджеты.
Например Iterations: 4, MaximalPoints: 4, MaximalLines: 0, MaximalCircles: 0
разрешают добавить до четырёх точек к исходным. Отбор применяется к каждому
добавлению; пользовательские условия автоматически не изменяются.

## Настройки

Оставлять средние 40% на каждом шаге:

```json
{
  "version": 1,
  "policy": "soft",
  "seconds": 600,
  "rankIntervals": [
    {"metric": "theoremsPerPoint", "from": 0.3, "to": 0.7}
  ]
}
```

0 — начало отсортированного списка, где теорем меньше; 1 — конец, где их больше.

| from / to | Какие продолжения разрешаются |
|---|---|
| 0 / 1 | Все; просмотр и расчёт рангов полностью пропускаются |
| 0.5 / 1 | Верхняя половина |
| 0.3 / 0.7 | Середина списка |
| 0 / 0.5 | Нижняя половина |

Пример «сначала много связей, затем мало фактов с новой точкой»:

```json
{
  "version": 1,
  "policy": "soft",
  "seconds": 600,
  "rankIntervals": [
    {"metric": "theoremsPerPoint", "from": 0.5, "to": 1}
  ],
  "finalRankInterval": {
    "metric": "newPointTheorems", "from": 0, "to": 0.5,
    "minimumNewTheorems": 1
  }
}
```

- theoremsPerPoint: сумма весов различных теорем полученной конфигурации / число точек.
- newPointTheorems: сумма весов теорем с единственной добавленной точкой.
  Для операции, добавляющей линию или окружность, это значение равно 0.
- По умолчанию веса теорем равны 1. Ранее доступные TypeWeights и
  LocalTheoremWeight могут их менять; оценка при этом становится взвешенной.
- minimumNewTheorems — необязательное минимальное число различных НОВЫХ
  утверждений, найденных GeoGen. Проверяется до ранжирования; по умолчанию 0.
  В примере 1 убирает из последнего списка варианты вообще без нового факта.
  Это не требование непростоты факта: прувер и Extending работают дальше.

При активном расчёте метрик поддерживаются до 63 явно названных точек.
Полный интервал без других оценок это ограничение не добавляет.

Каждая запись rankIntervals относится к одному добавлению объекта,
то есть к обычной итерации GeoGen. Можно задать разные записи на каждом шаге;
последняя повторяется. finalRankInterval заменяет её на последнем шаге,
допускаемом числом итераций и бюджетом типов добавляемых объектов.

Например, три независимых шага:

```json
{
  "version": 1,
  "policy": "soft",
  "seconds": 600,
  "rankIntervals": [
    {"from": 0.5, "to": 1},
    {"from": 0.3, "to": 0.7},
    {"from": 0, "to": 0.5}
  ]
}
```

Сам ранговый срез детерминирован при одинаковом списке и оценках. Поле seed
не фиксирует штатные случайные координаты исходной картинки в policy=soft;
численные картинки по-прежнему рисует обычный конструктор GeoGen.

## Полный интервал и округление

При [0,1] и minimumNewTheorems=0 используется обычный потоковый путь,
без предварительного построения детей и без вычисления их оценок.
Это проверено для трёх режимов симметрии и фильтров Fast/MemoryEfficient:
совпадают порядок, теоремы и число вызовов конструктора/finder.

Для чистого возврата к обычному GeoGen не включайте другие предпочтения:
оставьте keepOutsideTargetsPercent=100 (значение по умолчанию), не добавляйте
ограничений minimumNewTheorems. Сбор collectReference тоже выключен по умолчанию.

Если в допустимом списке M кандидатов, оставляются индексы
floor(from*M) ... ceil(to*M)-1. Индексация с нуля, верхняя граница не входит.
Для M=10 и [0.3,0.7] это индексы 3,4,5,6. На коротких списках доли
округляются наружу: например, половина из трёх — два кандидата.
Равные оценки разрешаются исходным порядком GeoGen. Поэтому часть одинаково
оценённых вариантов может быть отрезана; преимуществ друг перед другом
по выбранной метрике у них нет.

Сортировка нужна для определения разрешённого подмножества. Внутри него
DFS сохраняет исходный порядок, а не начинает с наибольшей оценки.

## Как сохраняется OnlySymmetric

Сохраняется исходная проверка, можно ли достроить конфигурацию до требуемой
симметрии при оставшихся итерациях, операциях и бюджетах. Она выполняется
до расчёта координат как при просмотре списка, так и в обычном verifier.
Выдача задач по-прежнему соответствует SymmetryGenerationMode.

Ранговый интервал задан для КАЖДОГО добавления. Поэтому в его список входят
и временно асимметричные конфигурации, которые штатный генератор разрешает
достроить. Их тоже можно отрезать выбранным интервалом. Это намеренное
ограничение ветвей, которое может исключить достижимую симметричную задачу.
В отличие от пороговых phases из SOFT_SEARCH.md, ранг не ждёт завершения
целого симметричного блока. Непустой интервал на списке из одного кандидата
сохраняет этот кандидат, например единственное завершение орбиты.

## Цена точности

1. Перечисляются все канонические дети родителя, допустимые по типам,
   HiddenPoints и бюджетам. Случайной порции из 16 и ограничения keep нет.
2. Невозможные симметричные завершения отсекаются до координат.
3. Остальные дети строятся, отбрасываются несуществующие и совпадающие
   с объектами родителя. Штатный TheoremFinder находит их новые теоремы.
4. Из полного допустимого списка после minimumNewTheorems берётся ранговый срез.
5. Выбранные определения в исходном порядке идут в обычный DFS.

Хранятся оценки и определения, а не координаты/контексты всех детей.
Выбранные дети при дальнейшем обходе строятся и анализируются повторно.
После отбора массивы отвергнутых кандидатов освобождаются. Старые кэши
выбранного ConfigurationFilter продолжают работать по своему алгоритму.

Предварительный просмотр требует памяти порядка числа детей и времени
на их полный обход. Он может задержать первую находку. Для частичного
интервала цена не пропорциональна его ширине: даже для 1% сначала нужен
весь список. При [0,1] этой цены нет.

Если бюджет закончился посреди просмотра, неполный список НЕ используется
как якобы точный. Поиск останавливается; журнал содержит complete=false.
MaxEvaluated учитывает также вызовы finder при предварительном просмотре.
seconds проверяется между кандидатами; долгий вызов канонизации/finder/прувера
может выйти за него, внешний --timeout остаётся предохранителем.

## Возврат к обычной генерации

Создайте отдельный JSON:

```json
{
  "version": 1,
  "policy": "soft",
  "seconds": 600,
  "keepOutsideTargetsPercent": 100,
  "collectReference": false,
  "rankIntervals": [{"from": 0, "to": 1}]
}
```

Не добавляйте minimumNewTheorems и частичный finalRankInterval. В таком виде
просмотра детей и вычисления рангов нет. Можно также запустить run совсем без
--search-config: будет обычная генерация, ограниченная внешним --timeout.

## Как подбирать профиль

Сначала запустите rank-all.json и сохраните число готовых задач, таймаутов
и время до первого факта. Затем меняйте один шаг, например оставьте полный
интервал на первых трёх добавлениях, а на четвёртом — [0,0.7] по
newPointTheorems. После этого сравните [0,0.5] и [0,0.3] на том же story.
minimumNewTheorems=1 можно включить отдельно, чтобы исключить продолжения без
нового утверждения. Значение 1 не означает одну нетривиальную задачу.

Для схемы «сначала много связей, потом мало» есть rank-good-then-bad.json.
Для осторожного эксперимента интервалы промежуточных шагов сначала держите
широкими, например [0.3,1] вместо [0.5,1]. Это профили предпочтений, не
подобранные оптимальные настройки. Не меняйте одновременно story, набор
построений, число итераций и расписание: причину результата будет трудно понять.

Узкий интервал всё равно требует полного просмотра. Сравнивайте не только
число оценённых конфигураций, но и факты после прувера, готовые задачи,
таймауты проверок, первую находку и время просмотра. Лучше несколько сюжетов
и повторных запусков. Seed не фиксирует исходные численные картинки в soft.

Не задавайте одновременно пороговые phases/final с
keepOutsideTargetsPercent<100, если хотите проверить влияние только рангов:
иначе применятся два независимых отбора. Не используйте --experimental-relations
вместе с --search-config. proposals/keep/explorationSlots/targetRatio из старого
batch-поиска не управляют rankIntervals; pictures в этом JSON тоже не меняет
штатное число картинок policy=soft.

## Где смотреть результаты и диагностику

| Путь внутри output | Содержимое |
|---|---|
| geo/ | Задачи, подготовленные для Geometry |
| results.tsv | Статусы, утверждения, рейтинги и результаты проверок |
| events/ | Исходные события GeoGen до проверки Extending |
| tasks/<id>/ | Рабочие файлы конкретной находки, worker.log и при наличии quality.json |
| geogen.log | Журнал генератора и ошибки |
| search-settings.json | Эффективные настройки, прочитанные C# |
| search-trace.jsonl | События и счётчики рангового поиска |
| tasks.sqlite | Состояние очереди и сохранённые события |

ready означает прохождение реализованных проверок; rejected — отбраковку;
timeout — нехватку времени проверки, а не доказанную тривиальность;
unchecked — пропуск Extending. sampled-valid означает успешные численные
пробы, а не математическое доказательство. Прочие статусы описаны в QUALITY.md.

Проверить последние события и суммарные счётчики:

```bash
tail -n 5 ./runs/rank-001/search-trace.jsonl
python3 - <<'PYTRACE'
import json
from pathlib import Path
p = Path("runs/rank-001/search-trace.jsonl")
for line in reversed(p.read_text().splitlines()):
    event = json.loads(line)
    if event.get("kind") == "finish":
        print(json.dumps(event, ensure_ascii=False, indent=2))
        break
else:
    print("Финальная запись ещё не появилась: поиск идёт или был остановлен извне")
PYTRACE
```

rank-pool-start означает начало просмотра детей одного родителя;
parentDepth=0 соответствует выбору первого добавления. rank-pool-finish:
count — число допустимых оценённых детей после minimumNewTheorems;
selected — сколько из них разрешено срезом; minimum/maximum — оценки всего
пула; milliseconds — время просмотра; complete=false — незавершённый пул.
Это не журнал оценок каждого кандидата по отдельности.

В финальных counters: RankCandidates — кандидаты до симметрии/координат;
RankSymmetryPruned — исключённые ранней проверкой симметрии;
RankDrawingAttempts — попытки построения; RankFinderCalls — вызовы finder
при просмотре; RankMetricsEvaluated — вычисленные оценки;
RankBelowMinimumNewTheorems — отбраковка по минимальному числу новых фактов;
RankSelected — разрешённые определения; RankingMs — суммарное время просмотра.
FinderCalls относится к обычному обходу, поэтому полная нагрузка finder —
FinderCalls+RankFinderCalls. Outputs — конфигурации до прувера, это не число
задач в events и не число прошедших Extending.

RankSelected может быть больше числа посещённых конфигураций: время могло
закончиться до обхода уже выбранных детей. При [0,1] счётчики Rank* равны нулю.
Если долго нет находок, посмотрите, завершился ли первый rank-pool и сколько
он занял. Сообщение о неподдерживаемом ранговом интервале означает, что
запущен старый комплект: git pull без build его не обновляет.

## Повторное открытие и параллельные запуски

Открыть уже созданный каталог в графической сессии:

```bash
"$suite" watch ./runs/rank-001
```

Продолжить обработку сохранённых событий, повторив error/timeout:

```bash
"$suite" resume ./runs/rank-001 --retry-errors --workers 1
```

resume восстанавливает обработку очереди; дерево поиска GeoGen для одиночного
run не восстанавливается. Для нового исследования нужен новый run/output.

Несколько генераторов можно запустить отдельными процессами с разными output:

```bash
"$suite" run ./examples/search/stories/altitudes-symmetric.txt \
  --search-config ./my-rank.json --output ./runs/rank-altitudes-001 \
  --timeout 660 --workers 1 --check-ms 2000 --standard-checks --quality-checks &
"$suite" run ./examples/search/stories/incircle-symmetric.txt \
  --search-config ./my-rank.json --output ./runs/rank-incircle-001 \
  --timeout 660 --workers 1 --check-ms 2000 --standard-checks --quality-checks &
wait
```

Они делят CPU и память. Для сравнения скорости профилей запускайте их
последовательно либо обеспечьте одинаковые выделенные ресурсы.

[Технический отчёт с фактическими десятиминутными результатами](RANK_SEARCH_REPORT.md).
Точный ранг числа теорем не гарантирует новизны, содержательности или уровня IMO-6.
