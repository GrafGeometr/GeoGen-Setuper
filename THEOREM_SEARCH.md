# Первый C#-прототип: архивное описание batch-режима

Для рангового отбора см. [RANK_SEARCH.md](RANK_SEARCH.md), для порогового
мягкого отбора — [SOFT_SEARCH.md](SOFT_SEARCH.md).
Следующее описание относится к policy=density/uniform и сохранённым профилям legacy-batches.

# Поиск по числу теорем: C#-прототип

Этот режим сначала строит очередной объект, затем находит теоремы новой
конфигурации и только после этого решает, продолжать ли её. Оценка аргументов
из старого Python-эксперимента не используется. Весь цикл построения,
поиска теорем, расчёта оценки и выбора ветвей выполняется внутри GeoGen на C#.
Python остаётся существующей оболочкой запуска и обработки результатов.

Режим пока экспериментальный. Никакая из его оценок не удостоверяет
сложность, новизну или соответствие задач уровню IMO-6.

## Сборка и запуск

Если репозиторий уже установлен после прошлого обновления:

```bash
cd /путь/к/GeoGen-Setuper
git fetch origin
git switch feature/family-discovery
git pull --ff-only origin feature/family-discovery
bash build.sh build --output ./dist/geometry-suite-native --test
```

Повторять `deps` не требуется, если системные зависимости уже установлены.
Сборка использует прежний `.builder`; старый готовый комплект сохраняется.
Если `dist/geometry-suite-native` уже существует, укажите другое новое имя.
Не нужно отдельно обновлять форк GeoGen: сборщик получает закреплённые
исходники и накладывает текущие патчи сборщика. Первый batch-прототип
поставлялся с 14 патчами; текущая версия включает 16.

Первичная установка:

```bash
git clone --branch feature/family-discovery https://github.com/GrafGeometr/GeoGen-Setuper.git
cd GeoGen-Setuper
bash build.sh deps
bash build.sh build --output ./dist/geometry-suite-native --test
```

Тестовый десятиминутный запуск на стандартных центрах треугольника:

```bash
./dist/geometry-suite-native/geometry-suite run \
  ./examples/search/stories/centers.txt \
  --search-config ./examples/search/policies/legacy-batches/balanced.json \
  --output ./runs/centers-native-001 --timeout 660 \
  --standard-checks --quality-checks --check-ms 2000 --view
```

Другие готовые сюжеты: `examples/search/stories/altitudes.txt` и
`examples/search/stories/incircle.txt`. Можно передать собственный story.
Копии примеров также лежат в `dist/geometry-suite-native/examples/search/`.
Параметры сюжета (построения, глубина, пределы объектов) по-прежнему берутся
из story. Каталог output должен быть новым; `--view` требует графической сессии.
При работе без окна уберите `--view`.

Без `--search-config` используется прежний полный перебор.
Сочетать режим со старым `--experimental-relations` нельзя.

## Один шаг поиска

1. Из допустимых операций случайно выбрать до B различных новых определений.
   Точки, линии, окружности и смешанные сигнатуры поддерживаются; HiddenPoints
   исключены из аргументов. Полный набор сочетаний не перечисляется.
2. Для каждого определения скопировать готовые координаты родителя и
   вычислить только новый объект штатным конструктором GeoGen. Отклонить
   несуществующие/совпадающие объекты и численно противоречивые конфигурации.
3. Штатным TheoremFinder найти новые теоремы, удалить устаревшие формы
   старых теорем. Сохранить обновлённый список вместе с координатами.
4. Посчитать метрику уже полученной конфигурации и её стоимость относительно
   цели текущей глубины.
5. Оставить до K продолжений: K−E лучших по стоимости и E случайных из
   оставшихся. Исследовать лучшее первым; остальные сохранены в стеке.
   В режиме uniform ранжирования нет, остальные вычисления те же.
6. Для оставленных конфигураций передавать новые теоремы обычному пруверу,
   затем в существующий поток Extending и проверок качества.

После обхода выбранного дерева поиск возвращается к исходной конфигурации
и делает новые случайные предложения. История уже проверенных конфигураций
ограничена MaxVisited; при переполнении сбрасывается. Поэтому повторные
посещения после сброса возможны. Состояние дерева на диск не сохраняется.

Симметричные переименования дедуплицируются только если они сохраняют
начальный сюжет и скрытые точки. При ограничении SymmetryGenerationMode
в выход передаются только соответствующие ему конфигурации.

## Что именно считается

Обозначим N — число явно присутствующих точек. Каждый различный Theorem
считается один раз. Разные утверждения на одной многоточечной прямой или
окружности остаются разными теоремами — геометрическое объединение их
в один объект здесь не производится.

Вес теоремы задаётся TypeWeights, по умолчанию 1. Дополнительно можно
уменьшить вес утверждений, которые целиком помещаются в одно построение
и его непосредственные аргументы: LocalTheoremWeight. Это синтаксическая
проверка, а не доказатель тривиальности; по умолчанию её множитель равен 1.

В обычном режиме:

```text
T = сумма весов теорем
D = T / (N + PointOffset)^PointExponent
```

Участие точки в теореме считается по явно названным точкам утверждения.
Для явно заданных прямых/окружностей учитываются их определяющие точки.
Предки самой точки автоматически в утверждение не добавляются.

NewPointDegree — сумма весов теорем с новой точкой. Если добавлена прямая
или окружность, статистика относится к совокупности её определяющих точек,
включая старые теоремы про них; это не отдельный счётчик утверждений про
новую прямую/окружность. NewPointOuterDegree считает
только те из них, где также участвуют точки вне непосредственных аргументов
нового построения. Второе число — доступная дополнительная настройка,
а не общий закон хорошей задачи.

Scope меняет расчёт D:

| Scope | Расчёт |
|---|---|
| all | Все теоремы / нормировка по всем N точкам |
| recent | Теоремы, затрагивающие хотя бы одну из последних RecentPoints точек / нормировка по числу этих точек |
| newest | Теоремы, затрагивающие новый объект / нормировка по одной точке |
| weakest | Средняя сумма весов теорем у RecentPoints наименее связанных точек; PointExponent/PointOffset здесь не применяются |

Это считает только типы утверждений, поддерживаемые существующим
TheoremFinder. Например, скрытые свойства биссектрис не появляются в числе
теорем автоматически. Поэтому нулевое число обнаруженных теорем не означает
отсутствия математических свойств.

## Стоимость и изменение цели по глубине

Для глубины d берётся Phases[d−1]; после конца массива повторяется
последний элемент. D0 — метрика исходной конфигурации.

```text
target = TargetDensity, если задан; иначе D0 × TargetRatio
cost = DensityWeight × |ln((D+0.5)/(target+0.5))|
     + NewPointWeight × |NewPointDegree−NewPointTarget| / NewPointScale
```

Меньшая cost предпочтительнее. Константа 0.5 позволяет сравнивать нулевые
значения. Коэффициенты — параметры поиска, не измерение сложности задачи.
Исходное значение D0, фактические D и степени точек записываются в лог.

## Настройки JSON

| Поле | Смысл / значение по умолчанию |
|---|---|
| version | 1 |
| seconds | 600 секунд всего поиска, включая время C#-прувера между выдачами |
| seed | 17; предложения и смешанные координаты воспроизводятся отдельно от времени остановки |
| pictures | 4 численные картинки; от 2 до 32 |
| mixedTrianglePictures | true: воспроизводимые остро-/тупоугольные треугольники вместо только остроугольных |
| proposals / keep | B=16 / K=4 |
| explorationSlots | E=1 случайное продолжение из K |
| policy | density или uniform |
| scope / recentPoints | all / 3 |
| pointExponent / pointOffset | 1 / 0 |
| typeWeights | Словарь имён типов GeoGen и неотрицательных весов; остальные равны 1 |
| localTheoremWeight | 1; понижение веса локальных утверждений необязательно |
| phases | Список целей и весов по глубинам |
| emitFromDepth | С какой глубины отдавать конфигурации пруверу, по умолчанию 1 |
| requireNonLocalTheorem | false; необязательное ограничение выдачи: требовать NewPointOuterDegree>0 |
| maxVisited | 50000 записей истории перед сбросом |
| maxEvaluated | Дополнительный лимит оценённых конфигураций; обычно не ограничен |
| logEveryExpanded | Прогресс каждые 20 раскрытий |
| traceFile / candidatesFile | Необязательные явные пути журналов |

Пределы точек, линий, окружностей, глубина и список построений по-прежнему
задаются в story. Текущий счётчик участия точек поддерживает до 63 точек
в одной конфигурации. Это предохранитель прототипа.

Готовые варианты: balanced, uniform, sparse, recent, strong-then-sparse.
Их можно скопировать и менять отдельно от кода. Это варианты для испытаний,
а не найденные оптимальные параметры.

## Результаты и измерения

В output сохраняются:

- search-settings.json — фактически использованные настройки;
- search-trace.jsonl — счётчики построений, отклонений, теорем, оценки выбранных
  продолжений, время конструктора/контекста/поиска теорем/метрики;
- search-candidates.jsonl — конфигурации и новые утверждения до прувера;
- events, results.tsv, tasks.sqlite, geo — обычные результаты после прувера
  и последующих проверок.

Время поиска проверяется между операциями. Один долгий вызов конструктора,
TheoremFinder или прувера может выйти за бюджет; внешний --timeout остаётся
предохранителем. После окончания поиска очередь проверок может обрабатываться
дополнительно. Время проверки очереди не входит в seconds.

Отмена эффекта режима: убрать --search-config и запустить в новом output.
Старые story и запуски не переписываются. Маркер SHA-256 проверяет соответствие
нового флага DLL. Результаты завершённых прогонов приведены в NATIVE_SEARCH_REPORT.md.

## Как подбирать параметры

Сначала скопируйте профиль: файлы в examples можно обновить следующим pull.

```bash
cp ./examples/search/policies/legacy-batches/balanced.json ./search-my.json
```

1. **Размер порции.** Сравните proposals=8,16,32,64 при неизменных keep=4,
   explorationSlots=1 и seconds=600. Это число случайных определений
   на одно раскрытие, а не список всех разрешённых операций. Геометрически
   допустимых детей после проверки может оказаться меньше. Число 16 —
   стартовая настройка, а не установленный оптимум.
2. **Количество сохранённых ветвей.** При выбранном proposals сравните keep=2,4,8
   (keep≤proposals). Больше keep сохраняет больше соседних вариантов,
   меньше keep чаще возвращает поиск к другим верхним построениям.
3. **Случайная часть.** Сравните explorationSlots=0,1,2 при keep=4.
   Это часть keep, а не дополнительные места. Она оставляет ветви,
   которые текущая метрика считает неудачными.
4. **Желаемая плотность.** Меняйте TargetRatio по глубине. Например,
   1.3,1.2,0.8,0.6 означает сначала повышенную, затем пониженную цель
   относительно исходного D0. Это именно цель: достижимость не гарантируется.
   Для абсолютных чисел вместо TargetRatio задавайте TargetDensity.
5. **Последняя точка.** NewPointWeight=0 отключает отдельное предпочтение
   для неё. Увеличение веса делает важнее NewPointTarget; например,
   target=1, weight=2, scale=1 сильно предпочитает одну найденную теорему.
   При малом весе плотность всей картинки может перевесить этот штраф,
   и будет выбрана точка с нулём теорем. Ноль теорем на последней глубине
   не даёт нового утверждения и может зря занять место среди keep.
6. **Вся картинка или часть.** Поменяйте scope на recent с recentPoints=3
   либо newest. Для слабейших точек есть weakest. Сравнивайте профили отдельно:
   численные значения разных формул имеют разный смысл.
7. **Формула.** PointExponent=1 даёт T/N, 2 даёт T/N². TypeWeights меняет
   вклад типов утверждений. LocalTheoremWeight можно снизить, чтобы уменьшить
   вклад утверждений внутри одного определения, но эта проверка синтаксическая
   и не заменяет доказательство тривиальности.

Меняйте одну группу параметров за раз. Используйте один story, одинаковые
число картинок и лимиты проверок. После первого сравнения повторите на seeds
17,18,19 и других сюжетах. Запускайте сравниваемые варианты последовательно
на одной машине; фоновые вычисления и число ядер влияют на результат.
Сравнение на 10 минутах — начальный бюджет; для тяжёлых входов нужны более
длинные серии, а не вывод по первым секундам без находок.

Пример последовательной серии по proposals; каждый запуск займёт до десяти
минут поиска и дополнительное время обработки очереди:

```bash
for n in 8 16 32 64; do
  python3 - "$n" <<'PYCFG'
import json, sys
n = int(sys.argv[1])
with open('search-my.json') as f:
    cfg = json.load(f)
cfg.update(proposals=n, keep=4, explorationSlots=1, seconds=600, seed=17)
with open(f'search-p{n}.json', 'w') as f:
    json.dump(cfg, f, indent=2)
PYCFG
  ./dist/geometry-suite-native/geometry-suite run ./examples/search/stories/centers.txt \
    --search-config "./search-p${n}.json" --output "./runs/p${n}-seed17" \
    --timeout 660 --workers 1 --check-ms 2000 --standard-checks --quality-checks
done
```

Для случайного контроля скопируйте профиль и поменяйте только policy на
uniform. При том же seed дальнейшие деревья разойдутся из-за другого отбора;
это не сравнение одних и тех же всех последующих конфигураций.

Смотрите `stream-status.txt` и `results.tsv`. В `search-trace.jsonl` последняя
запись finish содержит число Evaluated и время отдельных этапов. В progress
есть фактические оценки выбранных детей. Сравнивайте выход прошедших фильтры
задач за одинаковое время, а затем вручную сложность, содержательность и
повторы среди них. Число просмотренных конфигураций и близость к target —
диагностика поиска, а не критерии красоты. Timeout/error не считаются успехом.
Даже ready не является доказательством и не гарантирует уровня IMO-6.
